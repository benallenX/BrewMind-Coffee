# 04 — Risk Register

Likelihood and impact are rated Low / Medium / High against the MVP defined
in [01-product-goal-and-scope.md](01-product-goal-and-scope.md). This
register is expected to change as Phase 2 implementation surfaces new risks
or retires these; it is not a one-time document.

| Risk | Likelihood | Impact | Mitigation | Evidence required before release |
| --- | --- | --- | --- | --- |
| Uncontrolled scope growth | High | Medium | Hold the line on the MVP/out-of-scope split in [01-product-goal-and-scope.md](01-product-goal-and-scope.md); any addition requires an explicit scope-change decision, not silent inclusion. | Phase 2 implementation order (below) matches the approved scope with no unapproved additions merged. |
| Duplicate scheduled orders | Medium | High | Idempotency keys on recurring-order creation; unique constraint on (schedule, pickup date) at the database level; worker runs are safe to retry. | Test proving repeated/concurrent worker runs for the same schedule produce exactly one order. |
| Failed or delayed Stripe webhooks | Medium | High | Verify signatures, process webhooks idempotently, rely on Stripe's automatic retries, and reconcile subscription state on-demand (e.g. on dashboard load) rather than trusting webhook delivery alone. | Test simulating a delayed/replayed webhook and confirming no duplicate state change or lost payment confirmation. |
| Payment failure while a schedule remains active | Medium | High | Stripe subscription status drives an explicit "subscription inactive" state that pauses order generation; customer is notified. | Test confirming a failed-payment subscription stops generating new orders until resolved. |
| Timezone and daylight-saving errors | Medium | Medium | Store customer timezone explicitly; store recurring schedule times in a timezone-safe representation (local time + IANA timezone, not a naive UTC offset); compute each occurrence's UTC instant at generation time. | Test covering a schedule that spans a DST transition, confirming the pickup window does not shift. |
| Pickup-slot overbooking | Medium | High | Reserve pickup-window capacity inside the same transaction that creates the order; enforce a per-window capacity constraint at the database level. | Test with concurrent order-creation attempts against a nearly-full window confirming capacity is never exceeded. |
| Unavailable saved menu item | Medium | Medium | Check saved-drink availability at order-generation time; if unavailable, skip generation and notify the customer rather than silently substituting or failing. | Test disabling a product and confirming affected schedules produce a clear notification instead of a broken order. |
| Exposed secrets | Low | High | Secrets excluded from Git via `.gitignore`; Azure Key Vault in deployed environments; no secrets in logs. | Repository scan confirming no committed secrets; review confirming Key Vault is wired before first cloud deployment. |
| Insufficient authorization | Medium | High | Server-side ownership checks on every customer-record access; role checks on every staff/admin action; deny-by-default on missing checks. | Test suite covering cross-customer access attempts and role-boundary attempts, all rejected with `403`. |
| Database failure | Low | High | Automated backups; documented and tested restore procedure; PostgreSQL managed service in deployed environments. | A completed test restore from backup, with the RPO/RTO in [02-system-assumptions.md](02-system-assumptions.md) measured against it. |
| External service outage (Clerk, Stripe, Azure) | Low | Medium | Graceful degradation where possible (e.g. read-only dashboard if Stripe is down); clear user-facing error states instead of unhandled failures. | Manual test disabling network access to each dependency and confirming a controlled failure mode. |
| Azure cost growth | Medium | Medium | Stay on a single region/location for MVP; monitor cost against the capacity assumptions in [02-system-assumptions.md](02-system-assumptions.md); no premature scaling infrastructure (no Kafka/Redis/microservices). | Cost review against Azure budget before and shortly after first production deployment. |
| Excessive dependence on AI-generated code | Medium | Medium | All AI-assisted changes go through the branch workflow in [README.md](../../README.md) (feature branch → PR → automated testing → independent review → manual approval); no AI-generated change reaches `main` without human review. | CI and review-history evidence that the branch workflow was followed for all merged changes. |
